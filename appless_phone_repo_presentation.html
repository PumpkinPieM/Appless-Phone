1. 项目整体定位

Appless-Phone 更接近一个“AI Phone / Task-oriented Interface”原型，而不是传统的 App 启动器。

Agent 是入口

用户通过自然语言描述目标，Agent 决定调用哪些工具，而不是要求用户逐个打开 App 完成流程。

ReAct Tool Routing Multi-step

App 变成工具

高铁、航班、酒店、邮件、日历、地图、支付、社交等能力被抽象成固定或动态工具。

Provider Adapter MCP Composio

结果变成界面

工具执行后返回业务数据，代码侧 Builder 生成 A2UI JSONL，再由原生 ArkUI 或 HTML Surface 渲染。

A2UI JSONL Dynamic Surface

4. A2UI 生成链路

UI 的“描述”主要来自工具执行层，而不是主 LLM 的自然语言输出。

A2UI 数据管线 从业务结果到最终可见界面

当前实际行为

LLM 输出工具调用计划；工具和预定义 Builder 生成 A2UI 描述；Runtime 负责解析并渲染。

不是当前主链路

LLM 自由生成任意 UI DSL / 组件树，再由通用渲染器直接解释并生成完整 UI。

原生渲染路径

A2uiSurfaceState → A2uiSurfaceView

适用于 SocialHub 等需要更强原生交互的 Surface。

HTML 渲染路径

A2uiSurfaceState → HTML Document → HtmlHomeSurfaceView

多数业务结果通过 HTML Surface 呈现。

模型请求参数

字段值 / 作用
model由 LlmProvider 配置

Runner Prompt 的主要组成

组成部分在 Agent 中的作用示例
运行时上下文 提供设备当前时间等环境信息，帮助模型解析“今天、明天、下周”等表达。 Current device local datetime
ReAct 协议 规定模型使用 Thought、Execution、Action 或 Final 表达下一步。 Action: train.search({...})
工具目录 告诉模型当前可用的业务能力、参数格式、风险等级和适用场景。 train、flight、mail、calendar、maps
Persona / Skill / Memory 让同一个 Agent 以不同角色处理任务，并带入领域规则与长期偏好。 旅行搭子、Travel Planning、出行偏好
当前用户任务 描述本轮要完成的目标，是工具路由的直接输入。 查询明天深圳到上海的高铁
ReAct Scratchpad 在多步任务中保存前面步骤的模型输出和工具 Observation。 Thought → Action → Observation
Prompt 装配图 每一轮 ReAct 都会重新构造
Prompt 在这里扮演的是“工具编排协议”。

它的目标是让模型理解当前环境、选择合适工具并生成结构化参数； 最终业务界面仍由工具结果和 A2UI Builder 共同生成。

6. 实际云端模型请求示例

下面用一次“查询明天深圳到上海的高铁”的真实请求，说明运行时如何把用户任务、工具能力和角色上下文组织后发送给模型。

请求配置

模型deepseek-v4-flash
响应方式流式返回（stream: true）
Temperature0.2，偏向稳定的结构化输出
Thinking 配置disabled

这次请求要完成什么

用户目标是查询第二天从深圳到上海的高铁。Agent 需要：

  • 根据设备时间把“明天”解析为具体日期；
  • 识别这是铁路出行场景；
  • 选择 train.search；
  • 生成结构化查询参数；
  • 把工具结果交给 A2UI 链路展示。

messages 结构

SYSTEM

定义 Loop 的 Agent 身份和 ReAct 输出约定，要求模型只使用给定工具。

→
USER TASK

查询明天深圳到上海的高铁

→
RUNTIME AGENT CONTEXT

注入设备时间、工具目录、旅行 Persona、Skill、Memory、调用规则以及当前任务。

真实请求中的上下文组成 展示信息类别，不表示字符或 token 占比

旅行 Persona

实际请求中激活了“旅行搭子”角色。它负责路线比较、交通方式选择、出行节奏和用户偏好， 并要求实时班次、票价和余票必须来自工具。

Travel Planning Skill

Skill 进一步规定火车请求使用 train.search、航班请求使用 flight.search，并按耗时、换乘、价格和偏好组织结果。

9. 项目特点与演示重点

这一 Repo 的价值在于把 Agent 编排、真实工具调用和动态任务界面放在同一个 HarmonyOS 应用中展示。

Agent-first 交互

用户不需要先判断应该打开哪个 App，而是直接描述目标，由 Agent 负责选择能力和组织步骤。

工具化应用能力

旅行、邮件、日历、地图、支付、媒体和社交能力都以工具形式接入统一的 ReAct 循环。

任务型动态界面

界面围绕当前任务和数据生成，能够展示列表、卡片、确认流程和多任务聚合结果。

适合重点演示的能力

  • 自然语言触发高铁、航班、酒店或附近餐饮查询；
  • 多工具串行与并行执行；
  • Persona、Skill 与 Memory 对工具路由的影响；
  • A2UI JSONL 驱动的渐进式 Surface 更新；
  • 支付、发送、删除等动作的确认界面。

适合作为参考的技术主题

  • HarmonyOS Stage 模型下的 Agent 应用组织方式；
  • OpenAI-compatible 模型接入与 SSE 流式响应；
  • 工具注册、风险标注和 Provider Adapter；
  • 业务数据到动态 UI 协议的转换；
  • MCP、Composio 和固定工具共存的能力体系。
推荐的演示叙事 从用户体验逐步进入技术实现
一句话总结

Appless-Phone 的核心不是“LLM 直接生成任意 UI”，而是 “LLM 生成工具调用计划，业务工具返回真实数据，预定义 A2UI Builder 将数据转成动态任务界面”。
